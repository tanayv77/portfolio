Full-stack vehicle-history app

Secure used-car checks built around a FastAPI backend that mediates external vehicle data providers and assembles buyer-facing reports for an Android client.

Problem

Buyers have to cross-check MOT history, registration data, recalls, and seller context across disconnected services, usually on mobile.

What I built

A FastAPI backend with DVSA MOT, DVLA, recall, and company-context provider hooks, plus Kotlin/Compose flows for buyer briefs and report output. CameraX and ML Kit groundwork exists for plate capture.

Architecture

Android calls the backend. The backend owns OAuth, provider secrets, normalization, and report assembly before returning a mobile-ready summary.

Verification

API tests cover routes, recall fixtures, and capability checks against live provider responses. Mobile networking stays behind a Retrofit/Moshi boundary to the backend.

Scope / limits

Scope: backend-mediated report generation and provider aggregation. Production hosting, broader provider coverage, and deeper buyer-risk scoring still need hardening.

Local-first job runner

RunForge

Backend and platform engineering work for running container jobs, tracking lifecycle state, persisting events, and making background execution inspectable instead of opaque.

FastAPI PostgreSQL Docker WebSockets Migrations C++ helper

Technical highlight

Job state moves through queued, starting, running, and terminal states with persisted logs and retry gating, so failure handling is part of the system design.

Problem

Background jobs are easy to enqueue and hard to inspect once retries, logs, and failure states start piling up.

What I built

A FastAPI control plane, PostgreSQL state store, Docker execution path, worker service, persisted event logs, WebSocket status stream, health endpoint, and migration workflow.

Architecture

The API accepts work, persistence tracks jobs and runs, the worker loop advances lifecycle state, and containers execute payloads outside the control plane.

Verification

Tests cover API routes, persistence, worker transitions, integration paths, and in-process end-to-end execution. Local Docker is the strongest verified runtime today.

Scope / limits

Scope: local-first orchestration with inspectable runs. Kubernetes scaffolding exists, but cluster behavior and richer operator tooling are still follow-on work.

Problem

Global summaries can hide local structure, so boundary experiments need diagnostics that stay reproducible and sector-specific.

What I built

A Kerr versus Johannsen-Psaltis comparison pipeline with null geodesic boundary diagnostics, adaptive refinement-tree probes, structured outputs, audits, and manuscript support files.

Architecture

Verification

Scope / limits

Scope: draft research pipeline, not a published paper. The current claim stays narrow: sector-local adaptive diagnostics can expose JP deformation patterns that broad summaries miss.

About

Physics background, software first

I studied Physics, and that still shapes how I build software. I care about models, edge cases, measurement, and whether the output of a system can be checked instead of merely presented.

The strongest work here is not UI-first. It is backend-heavy, stateful, and often tied to awkward real-world boundaries such as government APIs, background execution, research diagnostics, or long-running simulations.

I still care about usability, but I treat it as part of the engineering job. If a report hides uncertainty, if a runner hides failure state, or if a research pipeline cannot reproduce its own claim, the system is not finished.
